Deduplication and decoded-partition reuse are implemented.

Changes validated on EC2 reduce host peak RSS by 119–148 MiB in the tested large-string cases. 01 / PRESERVE THE FIXPushed to main · 30846e0

Release the old schema before exporting the next one.

The fix in src/vgi_arrow_utils.cpp is on main. This was a proven ownership bug: buffered output reused a schema wrapper and lost its previous release callback. The diagnostic regression harness remains local benchmark work.

Acceptance: repeated queries leave zero live Arrow bytes after database close; the replacement-schema test passes; ordinary builds exclude the diagnostic hook.
Evidence and next action

The original four-column, 100,000-row workload leaked 76,800 bytes per query. The fix passed 120 repeated query checks across both reference workers, including nested/null values, dictionaries, large batches and cached replay. All 17 harness tests passed. A normal build without the probe passed another 24 query checks.

Next: preserve the original and fixed artifacts and retain the allocator regression with the benchmark setup. Collect a fresh quiet-host baseline from the normal build before assessing future performance changes.

Cases: buffered_t1, buffered_t4, schema_nested, schema_dictionary, schema_large_output, schema_cached.

02 / APPLY THE QUERY IMPROVEMENTDemonstrated experiment

Pass compact values into LATERAL functions.

Precompute the small function argument before the correlated join. In the measured query this changed the correlation key from a 16-KiB string to an integer, reducing Python host peak from 791 to 106 MiB.

Acceptance: identical results and row counts; the saved physical plan uses the compact key; the memory reduction repeats across fresh processes.
Query pattern and scope

Use the demonstrated rewrite where the function only needs the derived integer. Check that the projected argument has equivalent evaluation semantics, especially for volatile expressions.

There are two mappings: VGI already uses vgi_rpc.parent_row batch-local integer indices to associate worker outputs with inputs. DuckDB's enclosing delim/hash join separately correlates values. The experiment shrank that second key to the actual function argument. A unique row ID would be a different planner change, with different reuse behavior.

WITH t AS (
  SELECT c0,
         16 + CAST(substr(c0, 16361, 20) AS BIGINT) % 2 AS fanout
  FROM input_data
)
SELECT sum(length(c0))
FROM t, LATERAL bench.blended_explode(t.fanout) r;

Deliverable: update relevant query examples and retain a plan/memory comparison. Evaluate an automatic planner rewrite separately after proving where it is semantically valid.

Cases: lateral_fanout16, lateral_precomputed, lateral_native. The native control also had a large peak, locating much of this cost in join materialization.

03 / LARGE-STRING COSTImplemented and tested

Make deduplication sensitive to payload and cardinality.

VARCHAR/BLOB grouping now hashes existing buffers, verifies exact equality and samples large inputs before the full pass. Byte-work and comparison limits safely fall back to the original rows. Repeated strings retain their reduction in worker traffic; unique strings now approach the dedup-disabled memory control.

Acceptance: unique large inputs approach the dedup-disabled memory control, while repeated inputs retain reduced worker traffic and memory. Equality and null semantics stay exact.
Implementation approach and checks
  1. Read value lengths without copying their payload and estimate key cost before constructing canonical keys. Use a bounded, dispersed sample to estimate whether duplicates justify the work.
  2. For the existing canonical-key path, avoid the second owned copy by referencing its key buffer for the lifetime of the lookup.
  3. Evaluate a VARCHAR/BLOB path that hashes existing input buffers and stores representative row indices. Resolve hash collisions with exact value comparison; retain the canonical fallback for other types.
  4. Keep temporary-memory and comparison-work budgets. If the strategy becomes too costly, return the identity mapping and send the original batch. Preserve per-value cache behavior explicitly; do not toggle the global dedup setting as a shortcut.
  5. Test unique, highly repeated and mixed-cardinality inputs, including nulls, multiple columns and collision/equality edge cases.

Also benchmark a byte budget for outgoing string batches. Smaller RPC batches help only if upstream chunks, conversion buffers and queued batches stop keeping the original payload alive. Shorter table-in/out lifetimes remain an experiment, separate from the schema leak.

Cases: all scalar_dedup cases, scalar_strings_b64_vgi, scalar_strings_b2048_vgi, plus suites/string_batches.json and suites/string_length.json.

04 / REFERENCE-WORKER COSTDecoded cache implemented

Reuse decoded partitions and clean up execution metadata.

Rust now reuses decoded partitions across both window handlers, with persistent storage fallback, byte/entry limits and local destructor invalidation. Tests cover cache misses in another dispatcher, eviction, disabled caching and cleanup. The small durable argument records and ordinary listagg state updates remain separate follow-ups.

Acceptance: partition decoding scales with initialization/cache misses rather than every row; caches obey a byte budget; completed and cancelled executions release owned state.
Implementation approach and checks
  • Follow Python: populate a cache keyed by execution/partition at initialization, use it for both window handlers, reload from persistent storage on a miss, and evict on partition/execution destruction. Use shared Arrow buffers in Rust.
  • Add a byte budget as well as an entry cap. Python currently caps 256 entries; that is not a predictable byte limit for large partitions. Measure worker peak alongside decode counts and CPU.
  • Make the ordinary listagg fixture append efficiently. The append control still took about 165 seconds for 16,384 × 4-KiB values, so profile state serialization and SQLite access next.
  • Address the small retained aggargs records at execution end. Ten completed window queries plus EXPLAIN left 2,904 bytes of arguments after payload cleanup.
  • Do not clear an execution's arguments when just one partition finishes; other partitions can still need them.

Keep extension and SDK changes in separate comparisons with the other side's binary fixed. This step improves reference-worker behavior before using these workloads to rank frameworks.

05 / IDLE MEMORY POLICYLater experiment

Evaluate reclamation as a latency–memory tradeoff.

Arrow kept reusable pages after producer queries. In one retention test, releasing the pool after database close reduced host RSS from about 311 to 50 MiB while live Arrow allocations were already zero.

Acceptance: any idle-reclamation policy lowers retained RSS with an acceptable measured next-query cost. It must not conceal live allocation growth.
What to measure first

Compare no reclamation with explicit idle pressure or a carefully scoped idle trigger. Record RSS/PSS, live allocations, release duration and the latency of the next query. Avoid making per-batch global trimming the default without evidence.

The residual memory associated with unique-string deduplication is not fully attributed to an allocator yet. Resolve that ownership separately before classifying it as a second leak or assuming Arrow reclamation will fix it.

Next phase

Then assess all seven frameworks.

Once the extension baseline is stable, hold that binary fixed and run Python, Rust, C#, Java, Go, TypeScript and C++ through the same workload contract.

Make workloads comparable

Check fixture algorithms, null semantics, batch sizes and output equality first. Separate worker startup from warm execution, account for JIT warmup where relevant, and make unsupported capabilities explicit. Use equivalent algorithms for cross-language conclusions.

Explain each runtime's memory

Pair the shared host/worker accounting with runtime heap and CPU profiles. Distinguish live data, GC heaps, native Arrow allocations and idle runtime memory. Change one SDK at a time and retain its previous binary as the control.

The current measurements use owned subprocess workers over stdio. Add other transports as distinct comparisons after equivalent worker behavior is established.

Grounded in the completed investigation

Evidence, with its limits intact.

336 research trials; 1,023 completed measured query operations. Three large Rust window/listagg cases timed out at 300 seconds. Timeouts are preserved as failures. The shared EC2 host had unrelated compilation activity, so existing timings are diagnostic rather than CPU regression gates.

RSS is resident process memory; adding worker RSS counts shared pages more than once. PSS apportions those pages and better estimates combined physical memory. Live Arrow counters cover Arrow's pool, not every allocator. The 75-KiB leak figure is specific to the tested buffered workload.
