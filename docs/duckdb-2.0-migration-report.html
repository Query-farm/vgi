Engineering assessment

VGI is not a drop-in DuckDB 2.0 rebuild.

The extension reaches deeply into catalog, planner, expression, filter, function, physical-operator and secret APIs. The port is tractable, but it is a real compatibility project—and nested schemas require a protocol and data-model decision, not only C++ fixes.

Bottom line: your schema suspicion is correct. DuckDB 2.0 represents names as paths and permits schemas nested several levels deep. VGI currently collapses schema identity to one schema_name, so it cannot faithfully implement the new catalog contract without widening that model.

Evidence and scope

The assessment compares VGI’s current source against the local DuckDB 2.0 development branch and uses a compile-only probe to distinguish theoretical churn from APIs VGI actually touches.

VGI baseline

Haybarn-flavored DuckDB 1.5.5

VGI’s DuckDB submodule is 105edd31, tagged haybarn-v1.5.5-rc1. VGI itself was inspected at 588bb2fd. The native extension configuration hard-pins a matching Haybarn httpfs.

2.0 snapshot

Development branch, not a frozen ABI

The target was local branch v2.0-cyanoptera at a0315f712c (2026-09-09). This branch is still moving; re-run the probe at the revision ultimately chosen for release.

Probe

Header-substitution syntax check

VGI’s existing release compile commands were replayed with include paths pointed at DuckDB 2.0, using -fsyntax-only. Of 88 unique VGI source units, 46 passed and 42 failed.

Limit

Useful lower bound, not a completed build

The probe did not compile DuckDB, link VGI, load the extension, run SQL tests, exercise WASM, or include future Haybarn 2.0 patches. Error limits and shared headers also mask downstream failures.

Interpret the counts carefully. DuckDB’s merge-heavy development history makes the raw commit count noisy. More useful signals are the 42 failing VGI units, the concrete diagnostics, and the focused API commits cited below. All 179 DuckDB include paths used by VGI still exist; the problem is semantic/API churn, not wholesale header relocation.

Nested schemas: the architectural change

DuckDB 2.0 stops treating an object as the fixed tuple (catalog, schema, name). A QualifiedName holds a path whose final component is the object and whose preceding components can contain a catalog plus an arbitrarily deep schema chain.

Current mismatch

VGI has one flat schema set

VgiCatalog owns one VgiSchemaSet. Each VgiSchemaEntry owns tables, views, functions and macros, but no child-schema set and no parent pointer. Lookup uses only schema_lookup.GetEntryName(); scans are not recursive.

Wire mismatch

The RPC surface carries one string

Catalog list/get/create/drop/alter, function dispatch, scans, branches, statistics, writes and comments all pass schema_name. A dotted string is unsafe because quoted identifiers may themselves contain dots and case must remain meaningful.

DuckDB contract

New navigation hooks

EntryLookupInfo carries a full QualifiedName; SchemaCatalogEntry exposes GetParentSchema(), GetSchemaPath(), GetQualifiedName(), and detailed lookup. CreateInfo, DropInfo and AlterInfo now own qualified names.

2.0 limitation

Nested schemas are not a search path

The current engine deliberately rejects a nested schema in search_path / SET schema. Nested objects must be explicitly qualified. VGI should mirror this rather than inventing implicit resolution.

Recommended VGI design

  1. Introduce one lossless schema-path type at the catalog/RPC boundary: components as Identifier inside DuckDB-facing code and strings only in serialization.
  2. Add a child VgiSchemaSet and parent pointer to every VgiSchemaEntry. Override GetParentSchema(); support SCHEMA_ENTRY in lookup and scans.
  3. Navigate CreateSchemaInfo::ParentSchemas() and EntryLookupInfo::GetQualifiedName().Path(), matching DuckCatalog behavior. Make ScanSchemas recursive.
  4. Add schema_path to protocol payloads and capability-negotiate it. During transition, decode a missing path as [schema_name]; only emit the old field when path depth is one.
  5. Include the complete path in caches, global-function aliases, branch metadata, statistics keys, logs, transaction operations and invalidation. Otherwise identically named children under different parents collide.
  6. Test quoted path components, including an identifier containing .; never split or join identity using a literal dot.
Compatibility choice: VGI can compile first while rejecting nested schemas with an explicit “not supported by this worker protocol” error. That is a valid staging step. Silently reducing s1.s2 to s2 is not.

Concrete API adaptations

These are the replacements visible in VGI’s compile diagnostics and source paths.

2. Function registration and binding
  • Function signature state is encapsulated. Replace direct arguments, return_type, varargs, null_handling, stability and function_info access with current getters/setters and callback setters.
  • Scalar bind callbacks now receive BindScalarFunctionInput&; obtain context, arguments, binder and bound function from that input.
  • Function::EraseArgument is removed. Construct/mutate the new signature/parameter representation rather than editing the old vector.
  • FunctionSet is immutable/shared, and bound functions link to definitions. Audit code that copies a catalog function and mutates it after registration.
  • Runtime names passed to TableFunction, ScalarFunctionSet and AggregateFunctionSet must be wrapped as Identifier(name).
  • TableFunctionDynamicToStringInput / dynamic_to_string became TableFunctionToStringInput / to_string.

Primary VGI hotspots: vgi_extension.cpp, scalar/aggregate/table function sets and implementations, macro set, worker package and catalog API.

3. Expression and custom optimizer rewrites
  • BoundComparisonExpression is no longer an expression subclass. Use BoundComparisonExpression::Create(...) and inspect/manipulate the resulting BoundFunctionExpression through comparison helpers.
  • ExpressionClass::BOUND_COMPARISON (and old cast-class assumptions) no longer exist. Prefer expression type and helper predicates.
  • Parsed and bound expression members are private: use Left()/Right(), GetChildren(), Function()/FunctionMutable(), BindInfo(), GetReturnType()/SetReturnType(), Partitions(), OrderBy(), and window-bound accessors.
  • VGI’s multi-scan, required-filter, lateral batching, streaming-window and buffering rewrites should be ported as one cluster. They exchange bound expressions and table/column IDs, so partial conversion is risky.
4. Table filters—the highest silent-correctness risk

TableFilterSet::filters is private and indexes are ProjectionIndex. More importantly, runtime filters are now primarily ExpressionFilter objects containing arbitrary bound expressions, including multi-column expressions. The familiar constant/null/IN/conjunction/optional/dynamic classes remain only as Legacy* machinery for old serialization.

VGI currently walks the old enum tree in several places and directly reads/writes .filters. Replace that with the filter-set iterator (entry.GetIndex(), entry.Filter(), TakeFilter(), set/push/remove APIs) and serialize ExpressionFilter::GetExpressionFilter(...).expr by traversing the bound expression.

Do not mechanically rename old filter classes. VGI’s Top-N pushdown deliberately avoids serializing an uninitialized dynamic filter. In 2.0, use ExpressionFilter::IsOptionalFilter, IsRootOptionalFilter and GetRootOptionalDynamicFilterData to retain that behavior. Also carry all referenced column indexes; assuming one filter key equals one column can return wrong rows.
5. Table entries, values, vectors and includes
  • New late blocker: TableCatalogEntry::GetColumns() is now pure virtual and the base no longer moves info.columns. Add a VGI-owned ColumnList, initialize it from CreateTableInfo, and return it from the override.
  • Value became immutable. VGI’s BLOB→GEOMETRY fallback should return val.WithType(duck_type) instead of copying and calling Reinterpret. TryCastAs now returns optional<Value>.
  • Prefer Vector::Values<T>() and FlatVector::Writer<T>. VGI still has about 20 direct unified-format/flat-data references. Type-erased internals may keep unified format; typed aggregate-state loops should migrate.
  • Several failures are transitive-include cleanup: explicitly include binder_exception.hpp and the physical-plan-generator header where their types are used.
6. COPY, Arrow boundaries and callback names
  • COPY/table-function column names are vector<Identifier>. VGI’s Arrow schema helper still correctly wants string labels; call IdentifiersToStrings at that boundary.
  • PhysicalCopyToFile::rotate is no longer public; use Rotate(). The COPY operator’s rotation/abort/parallel lifecycle was reworked, so validate more than compilation.
  • Options maps are identifier-keyed. Wrap runtime keys or keep them typed instead of indexing with std::string.
  • Re-test partitioned output, per-thread output, byte-based file-size rotation, headers/empty output, temporary names and abort cleanup.
7. Logical IDs, interruption and profiling
  • VGI’s three custom logical operators override GetTableIndex() as vector<idx_t>; 2.0 requires vector<TableIndex>. Filter positions similarly use ProjectionIndex.
  • Replace direct ClientContext::interrupted reads with IsInterrupted(). Use InterruptCheck() at cooperative cancellation points so both explicit interrupts and max_execution_time deadlines are honored.
  • OperatorProfiler::GetOperatorInfo() is gone. Use GetOperatorMetrics(op).AddExtraInfo(key, value).
  • PhysicalOperator::ExtraSourceParams is gone. Move static display data to ParamsToString(); attach runtime data through current operator metrics where appropriate.
8. Secrets and lifecycle semantics
  • SecretStorage::DropSecretByName now accepts const Identifier&; VGI’s string override does not override anything in 2.0.
  • Secret/config key maps received Identifier propagation. Convert keys deliberately at external serialization boundaries.
  • DuckDB added connection- and transaction-scoped secret stores. Re-test VGI’s registered storage precedence, connection isolation, transaction rollback/commit, cleanup and same-name shadowing.

Runtime and behavioral risks after it compiles

The compile pass catches interface breaks. These areas can compile and still be wrong.

Correctness

Filter pushdown

Multi-column expression filters and optional dynamic filters change the semantic contract. A lossy serializer can over-filter remote data.

Lifetime

Catalog entries & indexes

Table column ownership changed and index lifetime was refactored. VGI’s deferred-drop graveyard, cached entry pointers, prepared statements and index metadata need ASAN/transaction stress tests.

Planning

Custom operators

Typed table IDs, private expression state, immutable function definitions and evolving physical planning can invalidate bindings across VGI’s custom rewrites.

Cancellation

Network and worker loops

Merely polling cancellation is insufficient if long RPC/subprocess waits never reach InterruptCheck(). Test explicit cancel and query deadlines on every transport.

Compatibility

Storage/protocol versions

DuckDB gates persistent nested-schema metadata on its 2.0 storage version. VGI’s own catalog protocol needs a corresponding capability/version story.

Semantics

Function definitions

Bound functions now link to immutable shared definitions. Any VGI pattern that mutates copied overloads at bind time needs explicit bind data instead.

Build, dependency and distribution work

A 1.5 extension binary is not a 2.0 artifact. All target variants and companion extensions have to move together.

  • Choose the actual engine first: stock DuckDB 2.0 or a future Haybarn 2.0 fork. The probe used stock 2.0 headers and removed the Haybarn version define; fork-only changes are therefore outside its scope.
  • Update VGI’s DuckDB submodule, then repin the hard-coded Haybarn httpfs, local ducklake, WASM httpfs, bundled extensions and extension-ci-tools to mutually compatible 2.0 revisions.
  • Revalidate DuckDB 2.0’s evolved extension build/signing/repository behavior, including external repository trust and namespaced install/load paths, against VGI’s distribution pipeline.
  • Build every supported platform from source: macOS/Linux/Windows, static/loadable, release/debug/reldebug and WASM/threads. Never attempt to reuse a 1.5 loadable binary.
  • No direct DuckDB C API dependency was found in VGI’s main extension integration, so the new C API is not currently a primary port item. Reassess any separately maintained host wrappers.
Pin a checkpoint. Because the inspected 2.0 branch is still changing—including a TableCatalogEntry break only days before this report—do the port against one recorded SHA and rebase deliberately, not continuously.

Recommended migration sequence

Freeze a target and add a dual-version branch

Record the DuckDB 2.0 SHA and stock-vs-Haybarn decision. Make CI expose both the existing 1.5 lane and an allowed-to-fail 2.0 lane until parity is reached.

Introduce compatibility types at VGI boundaries

Add identifier/string conversion helpers and a SchemaPath abstraction. Avoid scattering .GetIdentifierName() throughout business logic.

Port the catalog core

Fix GetDefaultSchema, qualified create/drop/alter/comment APIs, child schema sets, recursive lookup, table-owned columns, index names and path-aware cache identity. At this point basic attach/catalog DDL should compile.

Port functions, expressions and logical IDs

Adapt registration/bind APIs, private expression accessors, comparison helpers and typed table/projection indexes. Restore the custom rewriters and EXPLAIN output before touching optimization behavior.

Redesign filter serialization

Treat this as an isolated correctness deliverable: bound-expression serialization, multi-column bindings and dynamic optional filters, with differential tests against pushdown disabled.

Port execution edges

Update COPY, table-function names/callbacks, profiling, cancellation, Value immutability, vectors, secrets, custom writes and explicit includes. Perform a full link/load.

Widen the worker protocol

Add negotiated schema_path support to schemas, generated builders, server implementations and SDKs. Keep the one-level legacy bridge until all workers advertise the capability.

Repin and qualify the release matrix

Update companion extensions/tooling, run sanitizers and all platforms, then remove the 1.5 lane only after worker protocol rollout and compatibility tests pass.

Verification plan

The highest-value acceptance test is differential: execute with VGI pushdowns/rewrites enabled and disabled and require identical results.

  • Attach and enumerate top-level and three-level schemas
  • Quoted schema/object names, including dots and mixed case
  • Create/drop/rename/comment table, view, function and schema at depth
  • INSERT/UPDATE/DELETE/MERGE/RETURNING in nested schemas
  • Foreign keys, indexes and column changes across schema paths
  • Prepared statements survive cache invalidation/deferred drop
  • Filter comparisons, IN, NULL, AND/OR and struct extraction
  • Multi-column filters and expression filters
  • Top-N dynamic filters with NULLS FIRST/LAST
  • Filter pushdown enabled vs disabled differential results
  • Single/multi-branch scans and required filters
  • Streaming windows and lateral batching plan/result parity
  • COPY empty/header, parallel, partitioned and rotation paths
  • COPY/Parquet abort leaves no partial committed output
  • Explicit interrupt and max_execution_time per transport
  • Secret precedence, connection isolation and transaction rollback
  • Native and WASM; debug/reldebug with sanitizers/assertions
  • Loadability/signature tests from a clean install repository
