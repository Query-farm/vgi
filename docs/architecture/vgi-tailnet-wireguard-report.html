VGI over Tailscale and WireGuard

How VGI can become an easy, secure data-mesh substrate across laptops, offices, clouds, clusters, and partner environments—without creating a new protocol or coupling every worker SDK to one VPN vendor.

8/10Strategic fit

Strong idea—if VGI supports the overlay, rather than becoming the overlay.

Tailscale is an unusually good fit for VGI: it supplies encrypted peer connectivity, NAT traversal, stable naming, deny-by-default policy, service identities, and increasingly capable service routing. The best first release is not a new tailscale:// or wireguard:// wire transport. It is a hardened and productized way to run VGI’s existing raw TCP or HTTP protocol over an authenticated overlay.

Do now

Tailscale product profile

Fix hostname/IPv6 dialing, ship Serve and Services recipes, policy templates, container/Kubernetes examples, diagnostics, and a real integration suite.

Keep separate

Generic WireGuard

Document it as an operator-managed network. VGI already works over a WireGuard interface; VGI should not own peer keys, routes, DNS, or NAT traversal.

Later option

Embedded tsnet

Add an optional Go adapter where embedding a userspace tailnet node is valuable. Do not make a Go-only library the cross-language VGI contract.

The key finding: the data plane already exists

Tailscale and WireGuard are layer-3 overlays. VGI’s raw Arrow IPC runs over a bidirectional byte stream. The existing tcp://host:port transport is therefore already the correct data plane.

No VGI protocol fork is required. A worker reachable at a Tailscale IPv4 address can be used today as tcp://100.x.y.z:9400. A WireGuard interface address works the same way. HTTP workers likewise work over the overlay with ordinary http:// or https:// URLs.

What is already implemented

  • The core DuckDB extension detects tcp:// and uses the same framed Arrow RPC path as Unix sockets/subprocesses.
  • Python exposes serve_tcp, tcp_connect, Client.from_tcp, and worker --tcp.
  • Rust, Go, TypeScript, Java, C#, and C++ RPC ports all contain raw TCP server support.
  • The language ports consistently label raw TCP as having no built-in authentication or TLS and default it to loopback.
Fixed in working tree

The first concrete engineering gap

At the time of review, the core connector parsed a hostname from tcp://, but its native and Windows dialers fed that string directly to IPv4 inet_pton. The implementation now uses getaddrinfo, tries IPv4/IPv6 candidates under one connect budget, parses bracketed IPv6, and propagates resolver/connect diagnostics. Before that change:

  • Tailscale MagicDNS names do not reliably work.
  • Tailscale Service names do not work through this path.
  • IPv6 literals and DNS answers are unsupported.
  • DNS failures have poor diagnostics.

Why this distinction matters

Calling Tailscale a “transport” would collapse five independent concerns—wire protocol, routing, encryption, identity, and discovery—into one URI scheme. That would produce duplicated implementations, ambiguous security promises, and vendor lock-in. A clean architecture keeps those concerns composable.

Recommended architecture

Preserve VGI’s current protocol boundaries and add an overlay integration layer around deployment, resolution, policy, identity enrichment, and diagnostics.

Canonical endpoints

Keep tcp:// and https://

The endpoint says how VGI speaks to the worker, not which route the kernel uses. This also means any mesh—Tailscale, Headscale, plain WireGuard, Nebula, cloud VPN, private peering—can carry VGI without SDK changes.

Optional assertion

Add a network policy, not a network scheme

A future attach option such as NETWORK_REQUIRED 'tailscale' could reject a destination that does not resolve to an approved tailnet range/interface. It should be a fail-closed deployment assertion, not a second wire implementation.

Core connector change

Replace the direct IPv4 conversion in TcpConnect with a deadline-bounded resolver/dial loop:

  1. Parse RFC-compliant host/port authorities, including [IPv6]:port.
  2. Resolve with getaddrinfo(AF_UNSPEC, SOCK_STREAM).
  3. Attempt IPv6/IPv4 candidates under one overall connection deadline.
  4. Preserve TCP_NODELAY and cancellation behavior.
  5. Return actionable errors distinguishing invalid URI, DNS failure, policy denial/timeout, and connection refusal.

This unlocks MagicDNS, Tailscale Services, ordinary DNS, and IPv6 for everyone—not just Tailscale users.

Pilot only

Direct bind to a tailnet address

Bind the worker to its 100.x Tailscale address and attach by numeric IP. This proves the data plane immediately and preserves the remote source IP for identity lookup.

Trade-off: brittle addressing and a greater chance of binding the wrong interface. Do not recommend 0.0.0.0 as the easy path.

Recommended default

Loopback worker + Serve

Keep the unauthenticated worker on loopback. Let tailscaled accept only tailnet traffic and proxy raw TCP or HTTPS to it. The worker cannot accidentally appear on the LAN or public interface.

Trade-off: the backend sees the local proxy unless PROXY protocol is enabled and understood.

Production mesh

Tailscale Services

Publish a stable service name decoupled from hosts. Services add host approval, granular grants, traffic steering, regional routing, multiple hosts, and drain semantics. TCP is currently the supported transport, which matches VGI.

Trade-off: every host must present compatible catalog semantics and versions.

A practical raw-TCP pattern

# 1. A language-specific VGI worker listens only on loopback.
my-vgi-worker --tcp 127.0.0.1:9400

# 2. tailscaled exposes that port privately to the tailnet.
tailscale serve --bg --tcp=9400 tcp://127.0.0.1:9400

# 3. After the DNS fix, DuckDB uses the ordinary VGI TCP endpoint.
ATTACH 'risk_mesh' AS risk (
  TYPE vgi,
  LOCATION 'tcp://risk-worker.example-tailnet.ts.net:9400'
);

A stable, multi-host service pattern

# On each tagged service host; the local worker still listens on 127.0.0.1:9400.
tailscale serve \
  --service=svc:vgi-risk \
  --tcp=9400 \
  tcp://127.0.0.1:9400

# Tailnet policy: only VGI clients may reach this service and port.
{
  "grants": [{
    "src": ["tag:vgi-client"],
    "dst": ["svc:vgi-risk"],
    "ip": ["tcp:9400"]
  }]
}
Do not enable PROXY protocol yet. Tailscale Serve can prepend PROXY v1/v2 metadata to preserve the original client IP, but current VGI raw servers expect the Arrow IPC stream immediately. They would interpret the PROXY preamble as corrupt protocol data. Add explicit PROXY v2 parsing across the RPC ports before using that flag.

When HTTP is the better VGI transport

Use VGI HTTP over Tailscale when application-layer bearer/OAuth controls, resumable scans, externalized batches, compression, proxy compatibility, or browser/cloud integration matter more than raw streaming simplicity. Tailscale Serve can terminate HTTPS and proxy to a loopback HTTP worker. This is defense in depth: the tailnet gates network reachability while VGI can still authenticate the caller.

HTTPS certificates for *.ts.net names are convenient, but certificate names are published to public certificate-transparency logs. Worker names must not contain sensitive project or customer information.

Identity, authorization, and trust boundaries

WireGuard authenticates peer keys. Tailscale adds a control plane that maps nodes to users/tags and enforces grants. Neither automatically gives a raw VGI worker a portable application identity object.

Recommended security posture

  1. Bind raw workers to loopback by default. Publish them with Tailscale Serve or a controlled sidecar. Never make 0.0.0.0 the tutorial default.
  2. Use tagged machine identities for services. Grant the exact VGI client tag/group to the exact worker/service and port. Keep deny-by-default policy tests in version control.
  3. Retain VGI HTTP authentication for sensitive data. Tailnet membership is a reachability decision; it need not be the only data authorization decision.
  4. Trust injected identity headers only from the local Serve proxy. A directly reachable HTTP backend must strip or reject caller-supplied Tailscale-* headers.
  5. Do not use Funnel. Funnel is intentionally public. VGI’s mesh profile should detect and warn if the same port is configured for Funnel.
  6. Treat auth keys/OAuth client secrets as deployment secrets. Prefer short-lived or ephemeral tagged nodes for CI and transient workers; never bake reusable keys into images.

Phase-two identity contract

If data-level policies need caller identity, define one cross-language RPC concept instead of seven Tailscale-specific APIs:

PeerIdentity {
  network: "tailscale" | "wireguard" | "mtls" | "unknown",
  node_id?: string,
  user?: string,
  tags: string[],
  source_ip?: string,
  capabilities: map<string, json>,
  verified_by: "localapi" | "trusted_proxy" | "certificate" | "none"
}

Populate it from LocalAPI/tsnet, trusted Serve headers, PROXY v2 plus WhoIs, or mTLS as appropriate. Expose it through the existing request/call context. This keeps worker authorization code independent of the overlay vendor and makes verification provenance explicit.

Compatibility rule for Tailscale Services

A Tailscale Service may steer different connections to different hosts. VGI streaming state is connection-bound, so an individual raw-TCP stream remains naturally pinned. However, catalog attach/discovery and later execution can use separate connections. Every advertised host must therefore expose the same catalog identity, protocol compatibility, schema/version contract, authorization rules, and backing data semantics—or the service needs version-specific names such as svc:vgi-risk-v2.

Service drain is a good fit: it stops new connections while allowing existing VGI scans to finish. Rollouts should drain, wait for active connections, upgrade, verify, and re-advertise.

What “WireGuard support” should mean

Plain WireGuard creates a secure network interface and uses cryptokey routing: AllowedIPs both selects an outbound peer and constrains valid inbound source addresses. Once configured, VGI sees an ordinary IP route. That is enough for tcp:// and https://.

VGI-owned

Portable integration surface

  • DNS and IPv4/IPv6-capable dialing
  • Safe bind-address guidance
  • Connection diagnostics and timeouts
  • HTTP/mTLS option for application authentication
  • Documented firewall and liveness expectations
Not VGI-owned

VPN control plane

  • Peer key generation, storage, rotation, and revocation
  • AllowedIPs, routes, DNS, NAT traversal, keepalives
  • Service discovery, load balancing, device enrollment
  • Cross-company trust federation and incident response
  • Kernel/userspace tunnel lifecycle

Embedding these responsibilities in VGI would be a large, security-critical, permanent maintenance commitment. Organizations that want an open control plane can pair VGI with their selected WireGuard orchestrator (including Headscale-compatible Tailscale clients where appropriate) without changing VGI.

Proposed roadmap and effort

A useful release can be small. Identity-aware application authorization is valuable, but it should not delay the connectivity win.

Definition of done for the baseline

  • A user can copy a Python, Go, Rust, TypeScript, or Java example and serve a loopback worker through Tailscale without exposing a public/LAN listener.
  • DuckDB attaches with a MagicDNS or Tailscale Service name on macOS, Linux, and Windows.
  • The docs clearly distinguish transport encryption, network authorization, and application authorization.
  • An automated test proves attach + discovery + streaming through a real tailnet in an opt-in CI environment.
  • A diagnostic reports name resolution, destination addresses, route reachability, Tailscale connection type, service status, and likely policy failure without printing secrets.

Test and observability strategy

Correctness and failure matrix

  • Numeric IPv4, MagicDNS FQDN, short name, IPv6 literal, dual-stack result
  • Direct, DERP-relayed, and peer-relayed paths
  • Grant allowed/denied; service host pending approval; wrong port
  • Worker restart, client network roam, tailnet disconnect/reconnect
  • Service drain, rolling upgrade, host loss, incompatible host rejection
  • Large batches, long streams, cancellation, idle timeout, concurrent scans

Signals worth surfacing

  • Resolved endpoint(s), selected address family, connect duration
  • VGI transport and protocol versions—never credentials
  • Tailscale direct / peer-relay / DERP status when locally available
  • Peer identity verification source, without treating IP alone as identity
  • Bytes, batches, backpressure, reconnects, and time-to-first-batch
  • Clear hint: “TCP raw transport has no VGI-layer auth; overlay policy is the boundary”

Performance acceptance should separate VGI overhead from overlay path quality. Tailscale documents direct peer-to-peer connections as the lowest-latency/highest-throughput path; DERP is a reliable encrypted fallback with lower throughput. Record tailscale status/tailscale ping beside every benchmark so a relay regression is not misdiagnosed as an Arrow or VGI regression.
